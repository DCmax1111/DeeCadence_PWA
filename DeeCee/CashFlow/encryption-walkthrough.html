How password-protected local data could work

This separate, interactive demo shows each cryptographic step in your browser. It does not connect to Cashflow's ledger, save your text, or change the app's current storage.

Demonstration only — never enter real financial data or a password you use elsewhere.

This page keeps the example in memory and discards it when you reload or close the page. It has not been security-reviewed for production. The demo encrypts only the text you enter below.

1

Enter example data and a password

The browser will encrypt this text with a newly generated random data key. A password is used to protect that key, not to encrypt the text directly.

2

See the key setup

Data key: 256 random bits encrypt the example using AES-GCM. The key is random rather than derived from the password, so changing a password can re-wrap the same data key without re-encrypting all records.

Password key: PBKDF2 with SHA-256 and a unique random salt derives a wrapping key. The salt and iteration count are stored in the envelope; the password is not. AES-GCM wraps the data key.

Recovery key: an independent random secret derives a second wrapping key using HKDF-SHA-256. It can unwrap the same data key if the password is forgotten. Cashflow would not know or be able to retrieve this secret.

Authenticated encryption: AES-GCM protects confidentiality and detects modifications. Each encryption uses a fresh random nonce.

Save this recovery key somewhere safe

It is shown only for this demo session. Anyone with both the encrypted backup and this key can decrypt the backup. Losing both password and recovery key means the data cannot be recovered.

3

Inspect the encrypted envelope

The envelope contains ciphertext, salts, nonces, algorithm names, and two wrapped copies of the data key. It contains no password or readable example text. A production backup must be stored separately from the recovery key.

6

What this means for the real app

  • This demo does not encrypt, migrate, or read existing Cashflow data.
  • A real implementation must encrypt every persisted ledger field and ensure autosaves, exports, backups, and recovery all preserve the same protection.
  • Unlocking would expose data to the running app and device. Encryption does not defend against malware or someone using an unlocked session.
  • This demo shows password reset and optional recovery-key rotation, but it still needs careful security testing before real financial data is used.
